This chapter assesses the thesis: it assesses whether the objectives of §1.2 were met (§10.1), compares the requirements with the results (§10.2), summarises the conclusions about Kotlin Multiplatform and the lessons of the implementation (§10.3, §10.4), records the limits of the evaluation (§10.5) and proposes next steps (§10.6).

## 10.1 Assessment of the Academic Objectives

The academic motivation of the thesis (§1.2.1) rested on two architectural choices: using Kotlin across the whole system through Kotlin Multiplatform, so that a JVM backend, an Android application and a browser application share code, and designing by the principles of Clean Architecture and the Port/Adapter pattern, so that integrating and swapping external providers does not affect the core.

Using Kotlin across the whole system worked as designed. The :domain and :data modules are compiled from the same code for the JVM (backend and Android application) and wasmJs targets (§4.5.4); owner-web shows that Compose Multiplatform for the browser is adequate in practice for a full management application (Chapter 7); and the kiosk application uses the same DTOs in every request to the backend (§8.1). The backend–owner-web–kiosk chain works as one whole, with the same domain and data code in all three execution environments, and the full flow was verified through the API in an integrated environment (§9.3).

The Port/Adapter design also worked as expected. The six port interfaces of :domain (§4.4) are implemented both by adapters connected to real external services (email, company registry, geocoding) and by simulated ones (§6.6–§6.8). The business services do not know which adapter sits behind each interface, and replacing an adapter only affects the point where the dependencies are assembled (§6.4), with no change to a route, service or domain entity. The same pattern was applied in the Android application, where the card reader is hidden behind the CardTerminal interface (§8.5).

Whether the practical objectives per role (§1.2.2) were met is assessed in detail in §10.2.

## 10.3 Conclusions on Kotlin Multiplatform in Practice

The experience of implementing the system leads to three specific conclusions about the use of KMP.

First, shared code helps most where integration errors usually arise: in the consistency of DTOs between client and server. OrderResponse is exactly the same class in the backend, in owner-web and in the kiosk application (§7.1, §8.1), which avoids a whole category of type mismatch errors that, in a system written in several languages, would only appear at runtime. The benefit was especially noticeable when adding new features, such as food orders and payment on the device: the compiler checked every new field in a shared DTO at once everywhere it is used.

Second, the maturity of KMP is not the same for every compilation target. The combination of JVM (backend) and Android (kiosk) is very stable, since both rely on the same family of tools. The wasmJs target, to which owner-web is compiled, is noticeably newer: it was enough for the needs of the thesis, but its ecosystem (third-party libraries compatible with Wasm, debugging tools in the browser) is still smaller than that of an established JavaScript framework, and some browser capabilities, such as the Geolocation API, need direct interfacing with JavaScript. This cost was known early and was manageable.

Third, the architectural discipline of the monorepo structure (§4.1, §4.2) turned out to be especially useful, because the build system itself enforces it: :domain cannot gain a dependency on an external framework without a compilation error. This discipline does not prevent every design error, but it does prevent infrastructure decisions from leaking into :domain. This enforcement only holds at module boundaries, though: the backend's services live in the same module as the infrastructure and use the transaction mechanism directly (§4.2), which the compiler does not prevent.

## 10.4 Lessons from the Implementation

Beyond the conclusions about the technology, the implementation also produced lessons that apply more generally to a multi-tenant system with several clients. Most of them arose from specific errors that were found and fixed during development (§9.6).

Concurrency errors do not show up in single-user tests. The original payment flow checked whether an order had already been paid and then recorded the payment in a separate transaction; with one request at a time it worked correctly, but two almost simultaneous requests, such as a repeat from the kiosk after a network delay, could both pass the check. The fix was to lock the order's row at the start of the payment transaction, with a partial unique index in the database as the last safeguard, while the order's status changes are protected by compare-and-set (§5.6, §6.6). The conclusion is that every action that calls an external service or changes state should be designed from the start on the assumption that it may run concurrently with itself.

The state held by shared resources also needs particular care. A connection in the connection pool keeps the search_path setting it was given and returns to the pool to serve a request from another tenant. A setting that applies to the whole connection, and not only to the transaction, can therefore silently send a query to another tenant's schema. Using SET LOCAL and running all the statements that create a schema in one transaction (§5.1) greatly reduce this category of errors, and show that the isolation of schema-per-tenant is only as strong as the mechanism that selects the schema.

It is just as important to draw the trust boundaries clearly. The vulnerability in the choice of schema (§6.10) came from a value that the code treated as internal, the schema name, while at a public endpoint it was sent by the client. The fix was applied at a single point of control, through which every access to a tenant schema must pass, so that security does not depend on every route behaving correctly. The same logic was applied to prices and to the device's identity: whatever can be calculated or verified on the server is not accepted from the client.

Simulating an external service is most useful when it imitates the service's whole contract, including the way it notifies the system. The simulated delivery platforms inform the system through the same port (FoodOrderEventListener) that a real platform would use, so the core already treats the events as asynchronous, possibly late or duplicated. Real services, on the other hand, impose terms that a simulation does not have, such as the geocoding service's limit of one request per second or the company registry's request limits, and complying with them affected both the adapter and the interface (§6.8, §7.6).

Finally, errors can also hide in the details of a framework. One of the most time-consuming errors concerned the structure of the routes: when the devices' public and authenticated routes were declared in two separate trees, Ktor mapped a public request to an authenticated route and answered 401 (§6.1). Ktor's explicit route declarations (§4.5.2) helped to find the error, since the whole structure is visible in the code, but they did not prevent it.

## 10.5 Limits of the Evaluation

The assessment above concerns a system developed by a single programmer, in a demonstration environment with test data (seed data) rather than real production traffic, and should be read together with the implementation limitations recorded in §9.4. Two further factors limit the scope of the conclusions.

First, the Port/Adapter architecture allows the simulated services (§3.4.1) to be replaced without a change to the core, but it does not rule out integration issues specific to each provider (different protocols, error models, certification requirements), which cannot be evaluated without a real connection.

Second, the verification of the integrated flow was done through the API (§9.3) and not with automated unit or interface tests. Scale, for example the simultaneous operation of hundreds of tenants or thousands of kiosk devices, was not tested in practice, although the schema-per-tenant choice (§4.5.3) and stateless JWT (§4.5.7) in principle allow horizontal scaling. Some operations have a known linear cost in the number of tenants, such as resolving an activation code (§6.2) and updating the schemas at start-up (§5.1).

## 10.6 Proposals for Future Extension

Beyond the extensions that were placed out of scope from the start of the thesis (§3.4.4) and the extension to other countries (§3.4.3), the experience of the implementation points to the following directions.

Connecting a real payment acquirer, which owns charging, approval, PIN verification and refunds, would complete the payment flow (§8.5) without a change to the core of the system (§4.4).

The real APIs of the delivery platforms, where these are offered to partners, could be connected in the same way. Status notifications would then arrive through webhooks at the FoodOrderEventListener port, which has already been designed for this purpose (§6.7).

A push mechanism, such as WebSocket or Server-Sent Events, could replace periodic polling for updating the order status in the kiosk application and in the web panel; this would reduce the delay without a change to the state machine (§6.5), which is already independent of the transport mechanism.

Installing the system for production use needs further preparation: communication over TLS, exposing the backend only through the reverse proxy, a separate database role per tenant so that isolation is also enforced by database permissions (§9.4), storing the web panel's session in a mechanism safer than localStorage, a version table for updating the database structure, and systematic coverage with unit and integration tests.

Support for multiple languages in the interfaces would especially benefit the guest's application, which is aimed at an international audience.

Code sharing could also be extended to the interface: because the user interface code makes up the largest part of the system (§9.5), moving the kiosk application to Compose Multiplatform would allow the web panel and the Android application to share interface components, such as product cards and status indicators.

## 10.7 Closing Remarks

The thesis presented the design and implementation of a complete multi-tenant system of digital ordering and services for short-term rental accommodations, covering the hierarchy from the platform administrator to the guest. The prototype shows that a single language, Kotlin, can support a backend, an Android application and a web panel with shared code through Kotlin Multiplatform, and that the separation between the core and the infrastructure allows real and simulated services to be connected behind the same interfaces. With real payment and delivery providers connected and the installation prepared for production use, the system could serve as the basis of a service for real accommodations.
