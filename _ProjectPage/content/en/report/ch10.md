## 10.1 Assessment of the Academic Objectives

The academic motivation of the thesis (§1.2.1) was formulated as two testable questions: is Kotlin Multiplatform mature enough to support a JVM backend, an Android application and a browser environment from shared code at the same time; and can a system designed with strict Clean Architecture integrate and swap external providers without a change to its core.

The second question is answered positively and verifiably within the code itself. The six port interfaces of :domain (§4.4) are implemented by adapters of two kinds: real ones, connected to external services (SMTP, GEMI, Nominatim), and emulated ones, which simulate the payment acquirer and the food delivery platforms (§6.6–§6.8). The business services work with no knowledge of the kind of adapter behind each interface, and replacing an emulated adapter with a real implementation is limited to the point where the dependencies are assembled (§6.4), with no change to a route, service or domain entity. The same pattern was applied in the Android application, where the card reader is hidden behind the CardTerminal interface (§8.5). The coexistence of real and simulated implementations in the same prototype confirms the hypothesis in practice.

The first question is also answered positively. The :domain and :data modules are compiled simultaneously to JVM, Android and wasmJs without any divergence of code (§4.5.4); owner-web shows that Compose Multiplatform targeting the browser is practically suitable for a full management application (Chapter 7); and the kiosk application completes the cycle, since it is activated with a DEVICE-role JWT (§8.2) and uses it on every request to the catalogue, the orders and the payments. The backend–owner-web–kiosk chain works as an integrated whole, with the same domain and data code running through all three execution environments, and the full flow was verified through the API in an integrated environment (§9.3).

As regards the practical objectives per role (§1.2.2), the system meets the goal of the guest (ordering from the accommodation and from delivery platforms without an account, card payment on the device, stay information), of the owner (a single web panel, automated device activation, connecting delivery platforms, address search) and of the platform administrator (automated onboarding of owners with details from GEMI, audit log, settings of the external services).

## 10.3 Conclusions on Kotlin Multiplatform in Practice

The experience of implementing the system leads to three specific conclusions about the use of KMP.

First, the benefit of sharing code is greatest where most integration errors traditionally arise: in the consistency of DTOs between client and server. The fact that an OrderResponse is literally the same class in the backend, in owner-web and in the kiosk application (§7.1, §8.1) eliminates a whole category of type mismatch errors, which in a polyglot system would be discovered at runtime. The benefit was especially noticeable when adding new features, such as food orders and card payments: every new field in a shared DTO was caught by the compiler in all consumers at once.

Second, the maturity of KMP is not uniform across compilation targets. The combination of JVM (backend) and Android (kiosk) is exceptionally stable, since both rely on the same family of tools. The wasmJs target, to which owner-web is compiled, is noticeably newer: it worked adequately for the needs of the thesis, but the surrounding ecosystem (third-party libraries compatible with Wasm, debugging tools in the browser) remains smaller than that of an established JavaScript framework, and some browser capabilities, such as the Geolocation API, require direct interfacing with JavaScript. This cost was identifiable and manageable.

Third, the architectural discipline imposed by the monorepo structure (§4.1, §4.2) proves valuable because it is enforced by the build system: no dependency can be introduced from :domain to an external framework without a compilation error. This discipline does not prevent every design error, but it prevents the category of errors that Clean Architecture seeks to rule out: the leaking of infrastructure decisions into the core of the business logic.

## 10.4 Lessons from the Implementation

Beyond the conclusions about the technology, the implementation brought out a series of lessons that concern the engineering of a distributed, multi-tenant system more generally. Most of them came from specific errors that were found and fixed during development (§9.6).

The first lesson is that concurrency errors do not show up in single-user tests. The original payment flow checked whether an order had already been paid and then recorded the payment in a separate transaction; in tests with one request at a time it worked correctly, but two almost simultaneous requests, such as a repeat from the kiosk after a network delay, could both pass the check. The solution required a combination of row locking, compare-and-set and a database constraint as the last line of defence (§5.6). The conclusion is that every action that moves money or changes state must be designed from the start on the assumption that it will run concurrently with itself.

The second lesson concerns the state held by shared resources. A connection in the connection pool keeps the search_path setting it was given, and returns to the pool to serve the request of another tenant. A setting that applies to the whole connection, instead of only to the transaction, can thus silently direct a query to the wrong tenant's schema. Using SET LOCAL and running all the statements that create a schema in one transaction (§5.1) eliminate this category of errors, and show that the isolation of schema-per-tenant is only as strong as the mechanism that selects the schema.

The third lesson concerns trust boundaries. The vulnerability in the choice of schema (§6.10) came from a value that the code considered internal, the schema name, but which at a public endpoint came from the client. The fix was applied at a single point of control, through which every access to a tenant schema must pass, so that it does not depend on the correct behaviour of every route. The same logic was applied to prices and to the device's identity: whatever can be calculated or verified on the server is not accepted from the client.

The fourth lesson is that simulating an external service benefits from imitating its whole contract, including the way it notifies the system. The emulated delivery platforms inform the system through the same port that a real platform would use (FoodOrderEventListener), so the core already treats the events as asynchronous, possibly late or duplicated. The simulation does, however, have state of its own: its timers are lost in a restart, which led to the recovery mechanism of §6.7. Correspondingly, real services impose terms that do not exist in a simulation, such as Nominatim's limit of one request per second or GEMI's request limits, and complying with them affected both the adapter and the interface (§6.8, §7.6).

The fifth lesson concerns the details of the frameworks. One of the most time-consuming errors of development concerned the structure of the routes: declaring the devices' public and authenticated routes in two separate trees made Ktor match a public request against an authenticated route and answer 401 (§6.1). Ktor's explicitness (§4.5.2) made the error easier to find, since the whole structure of the routes is visible in the code, but it did not prevent it.

## 10.5 Limits of the Evaluation

The assessment above concerns a system developed by a single programmer, in a demonstration environment with seed data instead of real production traffic. Four factors delimit the scope of the conclusions.

First, the payment acquirer and the delivery platforms remain emulated (§3.4.1). The Port/Adapter architecture guarantees that replacing them requires no change to the core, but it does not guarantee that integration issues specific to each provider will not arise (different protocols, error models, certification requirements), which cannot be evaluated without a real connection. The three real integrations (SMTP, GEMI, Nominatim) nevertheless show that the same pattern also works against real services with timeouts, request limits and network errors.

Second, the verification of the integrated flow was done through the API (§9.3) and not with automated unit or interface tests. Scale issues, such as the simultaneous operation of hundreds of tenants or thousands of kiosk devices, were not examined empirically, even though the schema-per-tenant choice (§4.5.3) and the use of stateless JWT (§4.5.7) theoretically support horizontal scaling. Some operations have a known linear cost in the number of tenants, such as resolving an activation code (§6.2) and updating the schemas at start-up (§5.1).

Third, card payment depends on an Android device with a built-in card reader and the corresponding manufacturer service (§8.9). The application works on any device, but completing an order is possible only on a device with such a reader.

Fourth, kiosk operation in the fully locked state depends on enrolling the device as Device Owner, which was not carried out within the scope of the thesis (§8.3). This is an operational limit of the demonstration environment, independent of the core of the system.

## 10.6 Proposals for Future Extension

Beyond the extensions that were placed out of scope from the start of the thesis (§3.4.4), the experience of the implementation points to the following directions.

The first is connecting a real payment acquirer in place of the EmulatedPaymentAdapter, together with the real PIN check by the device's secure reader. The Port/Adapter architecture (§4.4) allows this with no change to the core. The second is the corresponding connection to the delivery platforms' real APIs, where these are offered to partners, with status notifications arriving through real webhooks at the FoodOrderEventListener port, which has already been designed for this purpose; the mechanism for recovering emulated orders at start-up (§6.7) would then no longer be needed.

The third direction is the move from periodic polling to a push mechanism, such as WebSocket or Server-Sent Events, for updating order status in the kiosk application and in the web panel; this would reduce the update delay without a change to the state machine (§6.5), which is already independent of the transport mechanism.

The fourth direction concerns maturing the installation for production use: communication over TLS, exposing the backend exclusively through the reverse proxy, storing the web panel's session in a mechanism safer than localStorage, a version table for updating the database structure, and systematic coverage with automated unit and integration tests. The fifth concerns support for multiple languages in the interfaces, especially in the guest's application, which is aimed at an international audience. The sixth concerns further code sharing: because the interface code makes up the largest part of the system (§9.5), moving the kiosk application to Compose Multiplatform would allow interface components, such as product cards and status indicators, to be shared between the web panel and the Android application.

Finally, extending to other countries would require an adapter of the CompanyRegistry port for the corresponding national business registry and a choice of country and time zone per accommodation (§3.4.3), while a courier or partner-store role would require new entities and tables in the tenant schema.
