## 4.1 Επισκόπηση Αρχιτεκτονικής και Δομή Modules

Το προτεινόμενο σύστημα υλοποιείται με τη μορφή ενιαίου αποθετηρίου κώδικα (monorepo), το οποίο περιλαμβάνει πέντε διακριτά modules που ορίζουν από κοινού τη λογική, τα μοντέλα δεδομένων και τις επιμέρους εφαρμογές της πλατφόρμας. Η επιλογή αρχιτεκτονικής τύπου monorepo διασφαλίζει ότι τα κοινόχρηστα modules (:domain και :data) συγχρονίζονται διαρκώς στην ίδια έκδοση για κάθε καταναλωτή, επιτρέποντας στον μεταγλωττιστή να εντοπίζει άμεσα οποιαδήποτε ασυμφωνία τύπων ή τροποποίηση συμβολαίου DTO ως σφάλμα μεταγλώττισης (compile-time error) σε όλες τις πλατφόρμες ταυτόχρονα, αποτρέποντας αστοχίες κατά τον χρόνο εκτέλεσης (runtime).

Τα πέντε modules της αρχιτεκτονικής διαρθρώνονται ιεραρχικά σε δύο επίπεδα: στα **κοινά modules** (:domain, :data) και στα **modules εφαρμογής** (:backend, :owner-web, :app).

Το module :domain αποτελεί τον ανεξάρτητο πυρήνα του συστήματος. Περιλαμβάνει τις κεντρικές επιχειρησιακές οντότητες (Order, Product, Device, Property), τα interfaces των repositories καθώς και τα port interfaces για τη διασύνδεση με εξωτερικές υπηρεσίες. Ο πυρήνας αυτός δεν εξαρτάται από κανένα εξωτερικό framework, βιβλιοθήκη υποδομής ή άλλο module του project. Αποτελείται από αμιγή κώδικα Kotlin και μεταγλωττίζεται ταυτόχρονα σε τρία διακριτά artifacts: Java bytecode (JVM jar) για το backend, βιβλιοθήκη Android (AAR/jar) για την εφαρμογή kiosk, και δυαδικό αρχείο WebAssembly (wasmJs bundle) για τον browser.

Το module :data εξαρτάται αποκλειστικά από το :domain και τη βιβλιοθήκη kotlinx.serialization. Ορίζει τα αντικείμενα μεταφοράς δεδομένων (Data Transfer Objects - DTOs), καθώς και τα αιτήματα και τις αποκρίσεις του REST API, υλοποιημένα ως @Serializable κλάσεις της Kotlin. Το module αυτό μεταγλωττίζεται επίσης και για τους τρεις στόχους (JVM, Android, wasmJs), αποτελώντας το κοινό συμβόλαιο επικοινωνίας μεταξύ server και clients.

Τα modules εφαρμογής εξαρτώνται από το :data (και μέσω αυτού από το :domain), τηρώντας αυστηρά τη φορά των εξαρτήσεων [24]:

- Το :backend αποτελεί εφαρμογή JVM που υλοποιεί το REST API μέσω του Ktor, αναλαμβάνει την πρόσβαση στη βάση δεδομένων μέσω του JetBrains Exposed και διαχειρίζεται τη σύνδεση με την PostgreSQL.
- Το :owner-web αποτελεί εφαρμογή διαχείρισης για τον browser, μεταγλωττίζεται σε WebAssembly (wasmJs) και εκτελείται μέσω του Compose Multiplatform.
- Το :app αποτελεί την εφαρμογή kiosk του καταλύματος για περιβάλλον Android, υλοποιημένη με Jetpack Compose.

Η φορά των εξαρτήσεων επιβάλλεται αυστηρά από το σύστημα δόμησης Gradle [24]: οποιαδήποτε κυκλική εξάρτηση ή προσπάθεια αναφοράς από το :domain προς το :data ή προς κάποιο module εφαρμογής απορρίπτεται άμεσα ως σφάλμα μεταγλώττισης.

## 4.2 Clean Architecture ως Δομικός Περιορισμός

Η αρχιτεκτονική του συστήματος ακολουθεί πιστά τις αρχές της Clean Architecture [5], όπως διατυπώθηκαν από τον Robert C. Martin. Θεμελιώδης κανόνας της προσέγγισης αυτής είναι ο Κανόνας Εξάρτησης (Dependency Rule): οι εξαρτήσεις του πηγαίου κώδικα κατευθύνονται πάντοτε προς τα μέσα, προς τα επίπεδα υψηλότερης πολιτικής και αφαίρεσης. Τα εξωτερικά επίπεδα (υποδομές, βιβλιοθήκες δικτύωσης, διεπαφή χρήστη, βάσεις δεδομένων) έχουν πλήρη γνώση του πυρήνα, αλλά ο πυρήνας διατηρείται σε απόλυτη άγνοια για οποιοδήποτε εξωτερικό στοιχείο.

Στο προτεινόμενο σύστημα, ο κανόνας αυτός επιβάλλεται ως δομικός περιορισμός του build system. Το module :domain έχει μηδενικές εξωτερικές εξαρτήσεις: δεν εισάγει το Ktor, δεν εισάγει το Exposed, ούτε οποιαδήποτε άλλη βιβλιοθήκη δεσμευμένη σε συγκεκριμένη πλατφόρμα. Κατά συνέπεια, ο κώδικάς του μεταγλωττίζεται αυτόνομα και πανομοιότυπα σε τρία ριζικά διαφορετικά περιβάλλοντα εκτέλεσης (JVM, Android, WebAssembly). Μια οντότητα Order που ορίζεται στο :domain αναπαρίσταται με την ίδια ακριβώς μορφή και σημασιολογία στον backend server, στο Android tablet και στον browser του ιδιοκτήτη.

Χαρακτηριστική εφαρμογή της αρχής αποτελούν τα repository interfaces. Το interface OrderRepository ορίζεται εντός του :domain και καθορίζει τις μεθόδους (method signatures) ανάκτησης και αποθήκευσης που απαιτεί η επιχειρησιακή λογική. Η συγκεκριμένη υλοποίηση (ExposedOrderRepository) κατοικεί στο module :backend, αξιοποιώντας το DSL του Exposed και τη βάση PostgreSQL. Σε ενδεχόμενη μελλοντική αντικατάσταση της PostgreSQL από άλλη τεχνολογία αποθήκευσης, η τροποποίηση περιορίζεται αποκλειστικά στο επίπεδο του :backend. Καμία οντότητα του domain, καμία υπηρεσία (service) και κανένα route δεν επηρεάζεται. Αντίστοιχα, η επιλογή του HTTP framework (Ktor) παραμένει μια λεπτομέρεια του εξωτερικού επιπέδου υποδομής, αφήνοντας ανέπαφο τον πυρήνα του συστήματος.

## 4.3 Multi-Tenancy — Αρχιτεκτονική Ροής Αιτημάτων

Το σύστημα οργανώνει τα δεδομένα και τα δικαιώματα πρόσβασης σε μια αυστηρή ιεραρχία πέντε επιπέδων: **Πλατφόρμα → Ιδιοκτήτης → Ακίνητο → Συσκευή → Φιλοξενούμενος**.

Ο Platform Admin ανήκει στο schema της πλατφόρμας (public) και έχει εποπτεία στο σύνολο του συστήματος. Κάθε ιδιοκτήτης (Owner) κατέχει ένα αποκλειστικό schema στη βάση δεδομένων (tenant\_{id}), εντός του οποίου καταχωρίζονται τα ακίνητα, οι συσκευές, τα προϊόντα και οι παραγγελίες του. Οι φυσικές συσκευές kiosk δεν διαθέτουν ξεχωριστό schema, αλλά συνδέονται μονοσήμαντα με ένα συγκεκριμένο ακίνητο του ιδιοκτήτη. Ο φιλοξενούμενος δεν διαθέτει λογαριασμό ή διαπιστευτήρια· η παρουσία του και η ένταξή του στο σωστό tenant schema προσδιορίζονται αυτόματα μέσω της πιστοποιημένης συσκευής kiosk που χρησιμοποιεί.

Η δυναμική δρομολόγηση κάθε εισερχόμενου HTTP αιτήματος στο κατάλληλο schema επιτυγχάνεται μέσω τεσσάρων συνεργαζόμενων μηχανισμών:

1. **Κρυπτογραφική ενσωμάτωση του Tenant Claim:** Κατά την ταυτοποίηση του χρήστη ή της συσκευής, το εκδιδόμενο JWT access token περιλαμβάνει το πεδίο (claim) schemaName (π.χ. tenant_a1b2c3 για έναν ιδιοκτήτη ή για μια ενεργοποιημένη συσκευή kiosk, και null για τον Platform Admin). Το claim αυτό είναι κρυπτογραφικά υπογεγραμμένο, αποκλείοντας οποιαδήποτε παραποίηση από την πλευρά του πελάτη.
1. **Επαλήθευση και εξαγωγή μέσω Middleware:** Το plugin ταυτοποίησης JWT του Ktor επαληθεύει την υπογραφή του token σε κάθε εισερχόμενο αίτημα και εξάγει την τιμή του schemaName.
1. **Διάδοση του TenantContext μέσω Coroutines:** Η τιμή του schema αποθηκεύεται σε ένα στιγμιότυπο TenantContext (υλοποίηση του CoroutineContext.Element), το οποίο διαδίδεται αυτόματα μέσω του coroutine scope σε όλη την ασύγχρονη αλυσίδα κλήσεων του αιτήματος, χωρίς να απαιτείται ρητή διαβίβασή του ως παράμετρος στις μεθόδους.
1. **Δυναμική επιλογή schema στη βάση δεδομένων:** Η συνάρτηση διευκόλυνσης tenantQuery {} ανακτά το TenantContext από το τρέχον coroutine scope, επαληθεύει ότι το όνομα του schema έχει την αναμενόμενη μορφή (tenant\_ ακολουθούμενο από δώδεκα δεκαεξαδικούς χαρακτήρες) και εκτελεί, ως πρώτη εντολή της συναλλαγής του Exposed, την εντολή SET LOCAL search_path TO {schemaName}. Κατά συνέπεια, η PostgreSQL ανακατευθύνει αυτόματα όλα τα SQL ερωτήματα της συναλλαγής στο σωστό schema. Η μορφή SET LOCAL περιορίζει τη ρύθμιση στη διάρκεια της συναλλαγής, ώστε μια σύνδεση που επιστρέφει στο κοινό connection pool να μην «κουβαλά» το schema ενός tenant στο επόμενο αίτημα, ενώ ο έλεγχος μορφής αποκλείει την εισαγωγή αυθαίρετου κειμένου στην εντολή SQL.

Μέσω αυτής της αρχιτεκτονικής, τα repositories δεν έχουν επίγνωση της multi-tenant φύσης του συστήματος: εκτελούν καθαρά ερωτήματα της μορφής SELECT \* FROM products, ενώ η υποδομή διασφαλίζει ότι το όνομα του πίνακα αντιστοιχεί πάντοτε στο schema του συγκεκριμένου tenant. Εάν ένα αίτημα επιχειρήσει πρόσβαση στη βάση χωρίς ενεργό TenantContext (π.χ. λόγω σφάλματος στο pipeline), η εκτέλεση διακόπτεται άμεσα με εξαίρεση ασφαλείας, αποκλείοντας την ανάγνωση ή αλλοίωση δεδομένων άλλου tenant.

## 4.4 Port/Adapter Pattern — Ενσωμάτωση Εξωτερικών Υπηρεσιών

Η ενσωμάτωση εξωτερικών υπηρεσιών χωρίς επιβάρυνση ή δέσμευση της επιχειρησιακής λογικής υλοποιείται μέσω του προτύπου Port/Adapter (Hexagonal Architecture) [9]. Σύμφωνα με το πρότυπο αυτό, ο πυρήνας της εφαρμογής αλληλεπιδρά με τον έξω κόσμο αποκλειστικά μέσω θυρών (port interfaces) που ορίζονται στο module :domain. Κάθε εξωτερική υπηρεσία αντιπροσωπεύεται από μία διεπαφή, ενώ οι συγκεκριμένες υλοποιήσεις (adapters) βρίσκονται στο module :backend και εγχέονται κατά την εκκίνηση της εφαρμογής μέσω μηχανισμού έγχυσης εξαρτήσεων (dependency injection).

Στο σύστημα ορίζονται έξι port interfaces:

- PaymentGateway: Port διασύνδεσης με τον αποδέκτη πληρωμών καρτών, για την έγκριση μιας συναλλαγής και την επιστροφή χρημάτων.
- FoodDeliveryProvider: Port διασύνδεσης με πλατφόρμες παραγγελίας φαγητού (efood, Wolt, Box): επαλήθευση του κλειδιού πρόσβασης, ανάκτηση εστιατορίων, μενού και καταλόγου προϊόντων, υποβολή και ακύρωση παραγγελίας.
- FoodOrderEventListener: Port αντίστροφης κατεύθυνσης, μέσω του οποίου μια πλατφόρμα ενημερώνει το σύστημα για την πρόοδο μιας παραγγελίας. Αντιστοιχεί στη διεύθυνση ειδοποιήσεων (webhook) που θα καλούσε μια πραγματική πλατφόρμα.
- NotificationService: Port αποστολής μηνυμάτων καλωσορίσματος και αποδείξεων μέσω ηλεκτρονικού ταχυδρομείου.
- CompanyRegistry: Port αναζήτησης των δημοσιευμένων στοιχείων μιας επιχείρησης με βάση τον ΑΦΜ.
- Geocoder: Port αναζήτησης διευθύνσεων και μετατροπής συντεταγμένων σε διεύθυνση.

Οι επιχειρησιακές υπηρεσίες (OrderService, PaymentService, OwnerService κ.ά.) επικοινωνούν αποκλειστικά με τις παραπάνω αφαιρέσεις, παραμένοντας πλήρως απομονωμένες από τα πρωτόκολλα επικοινωνίας, τις βιβλιοθήκες ή τις μορφές δεδομένων των συγκεκριμένων παρόχων.

Στο παρόν πρωτότυπο, τρία ports υλοποιούνται από adapters που συνδέονται με πραγματικές υπηρεσίες και δύο από emulated adapters (§3.4.1):

- Ο SmtpEmailAdapter αποστέλλει πραγματικά μηνύματα μέσω SMTP [33], με τις ρυθμίσεις του διακομιστή να διαβάζονται από τη βάση δεδομένων σε κάθε αποστολή.
- Ο GemhCompanyRegistryAdapter καλεί τη διεπαφή ανοικτών δεδομένων του ΓΕΜΗ [30].
- Ο NominatimGeocoderAdapter καλεί την υπηρεσία Nominatim [31], τηρώντας σε επίπεδο διεργασίας το όριο ενός αιτήματος ανά δευτερόλεπτο που ορίζει η πολιτική χρήσης της.
- Ο EmulatedPaymentAdapter αποφασίζει την έγκριση ή την απόρριψη μιας συναλλαγής με βάση τον τρόπο ανάγνωσης της κάρτας και το αποτέλεσμα του ελέγχου PIN.
- Οι EmulatedEfoodAdapter, EmulatedWoltAdapter και EmulatedBoxAdapter, με κοινή βάση την κλάση EmulatedFoodPlatformAdapter, διαβάζουν τα εστιατόρια, τα μενού και τους καταλόγους τους από αρχεία δεδομένων και αναφέρουν την πρόοδο κάθε αποδεκτής παραγγελίας μέσω του FoodOrderEventListener, του οποίου την υλοποίηση παρέχει η υπηρεσία FoodOrderEventHandler.

Η αρχιτεκτονική υπεροχή του προτύπου αποτυπώνεται στην ευκολία μετάβασης σε περιβάλλον παραγωγής: για την αντικατάσταση του EmulatedPaymentAdapter από τον adapter ενός πραγματικού αποδέκτη πληρωμών, απαιτείται αποκλειστικά η συγγραφή της νέας κλάσης στο :backend και η αλλαγή μίας γραμμής στη συνάρτηση configureRouting(), όπου συναρμολογούνται όλες οι εξαρτήσεις. Κανένα domain entity, κανένα service και κανένα route δεν απαιτεί τροποποίηση. Η συνύπαρξη πραγματικών και emulated adapters πίσω από διεπαφές της ίδιας μορφής αποτελεί, άλλωστε, την πρακτική επαλήθευση αυτής της ιδιότητας μέσα στο ίδιο το πρωτότυπο.

Ο τύπος κάθε παραγγελίας (type) καθορίζει ποια ports εμπλέκονται στη διεκπεραίωσή της. Μια παραγγελία προϊόντων του καταλύματος (IN_ROOM_STORE) τιμολογείται από τον κατάλογο του ιδιοκτήτη και εξυπηρετείται από τον ίδιο. Μια παραγγελία φαγητού (FOOD_DELIVERY) τιμολογείται από το μενού της πλατφόρμας μέσω του FoodDeliveryProvider, υποβάλλεται στην πλατφόρμα μετά την εγκεκριμένη πληρωμή και προωθείται στη συνέχεια από τα συμβάντα του FoodOrderEventListener. Η απόφαση αυτή λαμβάνεται εξ ολοκλήρου στο service layer, χωρίς καμία άμεση εξάρτηση από συγκεκριμένες υλοποιήσεις τρίτων.

## 4.5 Αποφάσεις Σχεδίασης και Επιλογή Τεχνολογιών

Κατά τη φάση σχεδίασης της αρχιτεκτονικής, αναλύθηκαν συστηματικά τα λειτουργικά και μη λειτουργικά χαρακτηριστικά των διαθέσιμων τεχνολογιών, αξιολογώντας τα αντίστοιχα trade-offs. Στις ενότητες που ακολουθούν τεκμηριώνονται οι βασικές σχεδιαστικές αποφάσεις.

### 4.5.1 Η Επιλογή Kotlin ως Μοναδικής Γλώσσας

Κεντρική σχεδιαστική απόφαση της εργασίας αποτέλεσε η υιοθέτηση **μίας και μόνης γλώσσας προγραμματισμού για ολόκληρο το stack λογισμικού** — από τον διακομιστή backend έως την Android εφαρμογή kiosk και το διαδικτυακό περιβάλλον διαχείρισης. Η επιλογή αυτή απορρέει άμεσα από την ανάγκη διασφάλισης απόλυτης συνέπειας τύπων σε ένα σύνθετο κατανεμημένο σύστημα.

Στην κλασική πολυγλωσσική προσέγγιση (polyglot architecture), το backend αναπτύσσεται συνήθως σε Java ή Go, η εφαρμογή Android σε Kotlin, και το web frontend σε TypeScript. Παρόλο που η προσέγγιση αυτή επιτρέπει τη χρήση εξειδικευμένων εργαλείων ανά πεδίο, εισάγει ένα σοβαρό μειονέκτημα: τον κατακερματισμό του κώδικα. Τα domain models, τα DTOs και οι κανόνες επικύρωσης υλοποιούνται πολλαπλές φορές σε διαφορετικές γλώσσες, δημιουργώντας διαρκή κίνδυνο αποκλίσεων και σφαλμάτων αποσειριοποίησης που αποκαλύπτονται μόνο κατά τον χρόνο εκτέλεσης.

Μέσω του **Kotlin Multiplatform (KMP)** [6], το πρόβλημα επιλύεται στη ρίζα του. Ο κοινός κώδικας που αναπτύσσεται στο commonMain source set μεταγλωττίζεται αυτόματα σε JVM bytecode για τον backend server, σε Android DEX bytecode για την εφαρμογή kiosk, και σε WebAssembly για τον browser. Οι οντότητες, τα DTOs και τα port interfaces ορίζονται άπαξ και επαναχρησιμοποιούνται αυτούσια. Οποιαδήποτε μεταβολή πεδίου ελέγχεται άμεσα από τον μεταγλωττιστή, παρέχοντας εγγυημένη ασφάλεια τύπων (end-to-end type safety).

Επιπρόσθετα, η Kotlin αποτελεί μια σύγχρονη γλώσσα με στατική ασφάλεια τύπων, αυστηρό έλεγχο μηδενικών δεικτών (null safety) και πλήρη ενσωμάτωση ασύγχρονου προγραμματισμού μέσω coroutines. Παρέχει ισοδύναμη απόδοση με την Java στο JVM, αποτελεί την επίσημη γλώσσα για το Android [10][11], ενώ μέσω της μεταγλώττισης WebAssembly προσφέρει υψηλή ταχύτητα εκτέλεσης στον browser. Σε επίπεδο παραγωγικότητας, η μονογλωσσία απλοποιεί δραστικά τη διαχείριση του έργου: ενιαίο σύστημα δόμησης (Gradle), κοινό περιβάλλον ανάπτυξης (IDE) και ενιαία νοητική αναπαράσταση για τον μηχανικό λογισμικού.

### 4.5.2 Backend Framework: Ktor έναντι Spring Boot και ASP.NET Core

Για την υλοποίηση του backend εξετάστηκαν τρεις επικρατούσες λύσεις: το **ASP.NET Core**, το **Spring Boot** και το **Ktor**.

Το **ASP.NET Core** αποκλείστηκε άμεσα, καθώς βασίζεται στο οικοσύστημα της C#. Η επιλογή του θα ακύρωνε τη στρατηγική του KMP, καθιστώντας αδύνατη την κοινή χρήση των modules :domain και :data στον εξυπηρετητή.

Το **Spring Boot** συνιστά το πλέον διαδεδομένο framework στο οικοσύστημα της JVM, διαθέτοντας υποστήριξη για την Kotlin. Εντούτοις, η αρχιτεκτονική του σχεδιάστηκε ιστορικά για την Java και βασίζεται σε εκτεταμένη χρήση reflection mechanisms και annotations (@Autowired, @Component, @RestController). Η προσέγγιση αυτή εισάγει υπονοούμενη συμπεριφορά (implicit behavior) και βαριά αυτοματοποιημένη διαμόρφωση (auto-configuration) [22], αποκρύπτοντας τη ροή εκτέλεσης. Επιπλέον, το Spring Boot επιβαρύνει την εκκίνηση με σημαντική κατανάλωση μνήμης και εισάγει πολυπλοκότητα στη συνεργασία του κλασικού του μοντέλου εκτέλεσης με τα Kotlin Coroutines.

Το **Ktor** [16], αναπτυγμένο από την JetBrains αποκλειστικά για την Kotlin, προσφέρει μια ριζικά διαφορετική φιλοσοφία. Στηρίζεται εξ ολοκλήρου στα Kotlin Coroutines, εξασφαλίζοντας μη μπλοκάρουσα (non-blocking) ασύγχρονη εκτέλεση σε κάθε αίτημα. Δεν χρησιμοποιεί reflection για τη δρομολόγηση, αλλά ένα δηλωτικό Kotlin DSL όπου κάθε route και παράμετρος ορίζονται ρητά στον κώδικα. Η αρχιτεκτονική του είναι πλήρως αρθρωτή (modular): κάθε επιμέρους λειτουργία (ταυτοποίηση, CORS, JSON serialization, status pages) εγκαθίσταται ρητά ως διακριτό plugin. Η ρητότητα αυτή ευθυγραμμίζεται απόλυτα με τις αρχές της Clean Architecture, καθώς όλες οι εξαρτήσεις και οι ροές ελέγχου παραμένουν ορατές και επαληθεύσιμες.

Ο παρακάτω πίνακας συγκρίνει τα τρία υποψήφια frameworks:

| Χαρακτηριστικό Σύγκρισης | Ktor | Spring Boot | ASP.NET Core |
|---|---|---|---|
| Γλώσσα & KMP Συμβατότητα | Native Kotlin (Πλήρης κοινή χρήση KMP) | Java / Kotlin (Μερική KMP αξιοποίηση) | C# (.NET — Ασύμβατο με KMP) |
| Μοντέλο Εκτέλεσης I/O | Non-blocking (Kotlin Coroutines) | Thread pool / Project Reactor (WebFlux) | Non-blocking (async / await) |
| Μηχανισμός Reflection | Μηδενικός (Ρητή δήλωση κώδικα) | Εκτεταμένος (Runtime annotations) | Μέτριος (Dependency injection reflection) |
| Φιλοσοφία Παραμετροποίησης | Explicit Modular Plugins via DSL | Convention over Configuration (Auto-config) | Middleware Pipeline Registration |
| Χρόνος Εκκίνησης & Μνήμη | Εξαιρετικά χαμηλός (\< 1 sec, \~50MB RAM) | Υψηλότερος (5–15 sec, 250MB+ RAM) | Χαμηλός (1–3 sec, \~80MB RAM) |

### 4.5.3 Στρατηγική Multi-Tenancy: Schema-Per-Tenant

Η επιλογή της στρατηγικής απομόνωσης στη βάση δεδομένων συνιστά κρίσιμη αρχιτεκτονική απόφαση [8][13]. Όπως αναλύθηκε στο Κεφάλαιο 2, εξετάστηκαν τρεις προσεγγίσεις:

1. **Shared Schema:** Παρουσιάζει ελάχιστο λειτουργικό κόστος, αλλά η ασφάλεια των δεδομένων επαφίεται εξ ολοκλήρου στην ορθότητα των ερωτημάτων της εφαρμογής (WHERE tenant_id = ?). Για ένα σύστημα που διαχειρίζεται εμπορικές συναλλαγές, ο κίνδυνος διαρροής δεδομένων λόγω προγραμματιστικού σφάλματος κρίθηκε απαράδεκτος.
1. **Database-per-Tenant:** Προσφέρει μέγιστη φυσική απομόνωση, αλλά εισάγει δυσανάλογη διαχειριστική επιβάρυνση (εκατοντάδες ανεξάρτητα connection pools, backup routines και ξεχωριστή εκτέλεση migrations ανά βάση), καθιστώντας την ασύμφορη για την κλίμακα της εφαρμογής.
1. **Schema-per-Tenant:** Αποτελεί τη βέλτιστη τομή απομόνωσης και λειτουργικής αποδοτικότητας. Κάθε tenant απολαμβάνει αυτόνομο namespace στην PostgreSQL, διασφαλίζοντας δομική απομόνωση σε επίπεδο βάσης δεδομένων. Παράλληλα, ολόκληρη η πλατφόρμα εξυπηρετείται από ένα ενιαίο, αποδοτικό connection pool (HikariCP), ενώ η δημιουργία νέου tenant απαιτεί απλή εκτέλεση DDL script εντός της ίδιας βάσης.

Ο παρακάτω πίνακας αποτιμά τις τρεις στρατηγικές:

| Παράμετρος Αξιολόγησης | Shared Schema | Schema-per-Tenant (Επιλογή) | Database-per-Tenant |
|---|---|---|---|
| Επίπεδο Επιβολής Απομόνωσης | Επίπεδο Εφαρμογής (WHERE φίλτρα) | Επίπεδο RDBMS (PostgreSQL Schema) | Φυσικό Επίπεδο (Ανεξάρτητη Βάση) |
| Αξιοποίηση Connection Pool | Βέλτιστη (Κοινό pool) | Βέλτιστη (Κοινό pool via HikariCP) | Κατακερματισμένη (Pool ανά βάση) |
| Κίνδυνος Διαρροής Δεδομένων | Υπαρκτός (σε περίπτωση bug στον κώδικα) | Μηδενικός (αποκλεισμός μέσω search_path) | Μηδενικός (πλήρης απομόνωση) |
| Διαχείριση Backup ανά Tenant | Εξαιρετικά σύνθετη | Απλή (pg_dump -n tenant_x) | Απλή (Backup όλης της βάσης) |
| Κόστος Υποδομής | Ελάχιστο | Χαμηλό / Προβλέψιμο | Υψηλό (γραμμική αύξηση πόρων) |

### 4.5.4 Κοινός Κώδικας: Kotlin Multiplatform

Η κοινή χρήση πηγαίου κώδικα μέσω του KMP επιλύει το ζήτημα του συγχρονισμού των διασυνδέσεων. Ο κώδικας του module :data (DTOs, αιτήματα και απαντήσεις) συντάσσεται άπαξ και μεταγλωττίζεται απευθείας στους αντίστοιχους στόχους.

Ο εξυπηρετητής backend σειριοποιεί σε JSON ένα αντικείμενο OrderResponse. Ο πελάτης (Android kiosk ή web panel) αποσειριοποιεί τα δεδομένα χρησιμοποιώντας την ίδια ακριβώς κλάση OrderResponse. Η ταυτότητα της κλάσης σε όλα τα επίπεδα αποκλείει εκ κατασκευής τα σφάλματα ασυμφωνίας πεδίων (type mismatches) ή ασυνέπειας ονοματολογίας, εξαλείφοντας την ανάγκη συντήρησης εξωτερικών εργαλείων παραγωγής κώδικα (code generators) ή schemas Swagger/OpenAPI για τον εσωτερικό συγχρονισμό του project.

### 4.5.5 Web Panel: Compose Multiplatform (wasmJs)

Για την ανάπτυξη του διαδικτυακού περιβάλλοντος διαχείρισης των ιδιοκτητών, η παραδοσιακή επιλογή θα ήταν η χρήση ενός JavaScript/TypeScript framework (όπως React ή Vue). Η υιοθέτηση του **Compose Multiplatform με στόχο μεταγλώττισης WebAssembly (wasmJs)** [21] υπαγορεύτηκε από την επιδίωξη απόλυτης αρχιτεκτονικής ομοιογένειας στο UI layer.

Το WebAssembly (Wasm) [14] αποτελεί συμπαγές δυαδικό format εντολών που εκτελείται εντός του sandbox του browser με ταχύτητα παραπλήσια της εγγενούς. Η υποστήριξη του WasmGC από τις σύγχρονες μηχανές περιήγησης επέτρεψε στη JetBrains να αναπτύξει τον στόχο Kotlin/Wasm, όπου ο κώδικας Kotlin μεταγλωττίζεται άμεσα σε Wasm χωρίς να απαιτείται βαρύ JavaScript runtime. Το Compose Multiplatform εκμεταλλεύεται τη δυνατότητα αυτή σχεδιάζοντας απευθείας τα γραφικά στοιχεία της διεπαφής σε επιφάνεια HTML5 Canvas.

Τα κύρια πλεονεκτήματα αυτής της επιλογής συνοψίζονται στα εξής:

1. **Ενιαίο Μοντέλο Προγραμματισμού UI:** Ο προγραμματιστής χρησιμοποιεί τις ίδιες δηλωτικές συναρτήσεις Composable, την ίδια διαχείριση κατάστασης (State) και τα ίδια αρχιτεκτονικά patterns τόσο στο Web όσο και στο Android.
1. **Απευθείας Επαναχρησιμοποίηση Κώδικα:** Το web panel καταναλώνει άμεσα τα Kotlin DTOs του module :data, χωρίς ενδιάμεσα interfaces μετατροπής.
1. **Ανεξαρτησία από το DOM:** Η απόδοση μέσω Canvas εξαλείφει τις αποκλίσεις εμφάνισης μεταξύ διαφορετικών browsers και απαλλάσσει την εφαρμογή από την πολυπλοκότητα των CSS frameworks.

Το βασικό trade-off της επιλογής έγκειται στο γεγονός ότι το οικοσύστημα του Kotlin/Wasm είναι νεότερο σε σύγκριση με τα καθιερωμένα εργαλεία της JavaScript, απαίτηση που αντισταθμίζεται πλήρως από τη συνοχή και την κοινή χρήση κώδικα που προσφέρει στο σύστημα.

### 4.5.6 ORM: JetBrains Exposed

Για την επικοινωνία με τη σχεσιακή βάση δεδομένων εξετάστηκαν τρεις προσεγγίσεις του οικοσυστήματος της JVM: το **Hibernate/JPA**, το **JOOQ** και το **JetBrains Exposed**.

Το **Hibernate/JPA** αποτελεί το παραδοσιακό πρότυπο ORM. Ωστόσο, στηρίζεται έντονα σε reflection, annotations και έναν πολύπλοκο κύκλο ζωής οντοτήτων (managed, detached, transient states). Επιπλέον, δεν διαθέτει εγγενή υποστήριξη για μη μπλοκάροντα coroutines, απαιτώντας ειδικές ρυθμίσεις για να μην δεσμεύει τα νήματα του Ktor.

Το **JOOQ** παράγει ισχυρό type-safe κώδικα βάσει υφιστάμενου schema βάσης (database-first προσέγγιση). Εντούτοις, απαιτεί ένα επιπλέον στάδιο παραγωγής κώδικα (code generation step) κατά τη διαδικασία του build, προϋποθέτοντας την παρουσία ενεργής βάσης δεδομένων για την παραγωγή των κλάσεων.

Το **Exposed** [15] ακολουθεί αντίστροφη, code-first προσέγγιση μέσω Kotlin DSL:

- Η δομή των πινάκων ορίζεται άμεσα στον κώδικα ως Kotlin αντικείμενα (Table objects), καθιστώντας τον πηγαίο κώδικα τη μοναδική πηγή αλήθειας για τη δομή της βάσης.
- Τα ερωτήματα συντάσσονται με πλήρη ασφάλεια τύπων (type-safe DSL), όπου ο μεταγλωττιστής επαληθεύει τα ονόματα των στηλών και τους τύπους δεδομένων ήδη κατά το build.
- Υποστηρίζει εγγενώς ασύγχρονη εκτέλεση μέσω της συνάρτησης suspendTransaction, ενσωματώνοντας ιδανικά τις συναλλαγές στο περιβάλλον των Kotlin Coroutines.
- Λειτουργεί χωρίς reflection και runtime annotations, διατηρώντας τη σαφήνεια και την ταχύτητα εκτέλεσης.

Ο παρακάτω πίνακας συνοψίζει τη συγκριτική αξιολόγηση των ORM εργαλείων:

| Κριτήριο Αξιολόγησης | JetBrains Exposed (Επιλογή) | Hibernate / JPA | JOOQ |
|---|---|---|---|
| Ορισμός Schema (Source of Truth) | Code-first μέσω Kotlin Table DSL | Code-first μέσω Java Annotations | Database-first μέσω Code Generation |
| Ενσωμάτωση με Coroutines | Εγγενής (suspendTransaction) | Απαιτεί εξωτερικό thread bridging | Απαιτεί Reactive Extensions / R2DBC |
| Μηχανισμός Reflection | Μηδενικός | Εκτεταμένος κατά το runtime | Μηδενικός (παραγόμενος κώδικας) |
| Εξάρτηση από Live DB στο Build | Καμία | Καμία | Απαιτείται για το generation |
| Ευκολία Multi-Schema Routing | Άμεση υποστήριξη SET search_path | Σύνθετη παραμετροποίηση Multi-tenancy | Υποστηρίζεται μέσω configuration |

### 4.5.7 Ταυτοποίηση: JWT με Refresh Token Rotation

Η διαχείριση των συνεδριών και της πρόσβασης υλοποιείται μέσω **stateless JSON Web Tokens (JWT)** [18] σε συνδυασμό με **μηχανισμό ανανέωσης με εναλλαγή (Refresh Token Rotation)** [19].

Ανεξάρτητα από τον τύπο του token, όλοι οι κωδικοί πρόσβασης των χρηστών αποθηκεύονται στη βάση δεδομένων αποκλειστικά ως κρυπτογραφικά hashes μέσω του αλγορίθμου **BCrypt** με cost factor 12 [20]. Ο συντελεστής αυτός επιλέχθηκε ώστε ο υπολογισμός να διαρκεί περίπου 250ms σε σύγχρονο επεξεργαστή, καθιστώντας ασύμφορες τις επιθέσεις λεξικού ή brute-force, χωρίς να επιβαρύνει την εμπειρία σύνδεσης του χρήστη.

Η αρχιτεκτονική επιλογή εξετάστηκε έναντι της κλασικής ταυτοποίησης μέσω συνεδριών με διατήρηση κατάστασης (stateful server sessions):

| Παράμετρος Σύγκρισης | Stateless JWT με Token Rotation (Επιλογή) | Stateful Server Sessions (Cookies) |
|---|---|---|
| Οριζόντια Κλιμάκωση (Scalability) | Άμεση (Κανένας διαμοιρασμός μνήμης μεταξύ servers) | Απαιτεί distributed session cache (π.χ. Redis) |
| Επιβάρυνση Βάσης ανά Request | Μηδενική (Επαλήθευση κρυπτογραφικής υπογραφής) | Υποχρεωτικό query ανάκτησης session σε κάθε κλήση |
| Διάρκεια Έκθεσης Access Token | Ελάχιστη (Σύντομος χρόνος ζωής 15 λεπτών) | Εξαρτάται από το session timeout |
| Ανάκληση Πρόσβασης | Άμεση μέσω ακύρωσης του refresh token | Άμεση μέσω διαγραφής του session |
| Κατάλληλο για Ετερογενείς Clients | Ιδανικό (Κοινό HTTP Authorization header) | Ευάλωτο σε περιορισμούς CORS και WebAssembly |

Το access token έχει σκόπιμα σύντομη διάρκεια ισχύος (15 λεπτά για χρήστες και διαχειριστές), περιορίζοντας δραστικά το χρονικό παράθυρο απειλής σε περίπτωση υποκλοπής. Το refresh token έχει διάρκεια ισχύος 30 ημερών και χρησιμοποιείται αποκλειστικά για την έκδοση νέου access token χωρίς επαναληπτική εισαγωγή διαπιστευτηρίων.

Η ασφάλεια ενισχύεται μέσω του μηχανισμού **Refresh Token Rotation**: κάθε φορά που ένα refresh token χρησιμοποιείται για ανανέωση, διαγράφεται από τη βάση δεδομένων πριν από την έκδοση του νέου ζεύγους tokens. Ένα ήδη χρησιμοποιημένο refresh token δεν μπορεί επομένως να χρησιμοποιηθεί ξανά (replay attack), καθώς δεν αντιστοιχεί πλέον σε καμία εγγραφή. Η ανανέωση απορρίπτεται επίσης αν ο λογαριασμός του ιδιοκτήτη έχει απενεργοποιηθεί στο μεταξύ, ενώ κάθε αίτημα ιδιοκτήτη προς τα δεδομένα του tenant ελέγχει ότι ο λογαριασμός παραμένει ενεργός, ώστε η απενεργοποίηση να ισχύει από το επόμενο αίτημα και να μην αναμένει τη λήξη του access token. Ο ίδιος ο χρήστης μπορεί να αλλάξει τον κωδικό του· η αλλαγή διαγράφει όλα τα refresh tokens του, τερματίζοντας τις υπόλοιπες συνεδρίες του, και επιστρέφει νέο ζεύγος tokens για την τρέχουσα.

Οι συσκευές kiosk αποτελούν διαφορετική περίπτωση. Μια συσκευή δεν συνδέεται με κωδικό και δεν χρησιμοποιεί refresh token· λαμβάνει κατά την ενεργοποίησή της ένα access token με ρόλο DEVICE και διάρκεια ισχύος ενός έτους. Για να μην εξαρτάται η ανάκληση της πρόσβασης από τη λήξη του token, το backend ελέγχει σε κάθε αίτημα συσκευής ότι η αντίστοιχη εγγραφή υπάρχει και είναι ενεργή· η απενεργοποίηση ή η αποσύνδεση μιας συσκευής από τον ιδιοκτήτη ισχύει έτσι από το επόμενο κιόλας αίτημά της. Ο έλεγχος αυτός κοστίζει ένα επιπλέον ερώτημα ανά αίτημα συσκευής, το οποίο θεωρήθηκε αποδεκτό τίμημα για την άμεση ανάκληση.

Επιπρόσθετα, τα refresh tokens δεν αποθηκεύονται σε απλό κείμενο στη βάση δεδομένων: αποθηκεύονται αποκλειστικά ως κρυπτογραφικά hashes μέσω της συνάρτησης **SHA-256** [29]. Σε ενδεχόμενη παραβίαση του πίνακα refresh_tokens, τα καταγεγραμμένα hashes είναι άχρηστα για έναν επιτιθέμενο, καθώς η ταυτοποίηση προϋποθέτει την κατοχή του αρχικού, μη κρυπτογραφημένου token.

### 4.5.8 Κρυπτογράφηση Μυστικών των Εξωτερικών Υπηρεσιών

Η ενσωμάτωση εξωτερικών υπηρεσιών απαιτεί την αποθήκευση μυστικών στοιχείων: του κωδικού του διακομιστή SMTP, του κλειδιού πρόσβασης του ΓΕΜΗ και των κλειδιών πρόσβασης των πλατφορμών διανομής κάθε ιδιοκτήτη. Σε αντίθεση με τους κωδικούς των χρηστών, τα στοιχεία αυτά δεν μπορούν να αποθηκευτούν ως hash, καθώς το backend πρέπει να τα ανακτά αυτούσια για να τα χρησιμοποιήσει. Εξετάστηκαν δύο προσεγγίσεις: η διατήρησή τους σε μεταβλητές περιβάλλοντος του server και η αποθήκευσή τους κρυπτογραφημένων στη βάση δεδομένων.

Οι μεταβλητές περιβάλλοντος είναι κατάλληλες για ρυθμίσεις που ορίζονται μία φορά κατά την εγκατάσταση, όμως απαιτούν επανεκκίνηση του server για κάθε αλλαγή και δεν μπορούν να αποθηκεύσουν στοιχεία που διαφέρουν ανά tenant, όπως τα κλειδιά των πλατφορμών κάθε ιδιοκτήτη. Επιλέχθηκε επομένως η αποθήκευση στη βάση δεδομένων με συμμετρική κρυπτογράφηση **AES-256 σε λειτουργία GCM** [34], η οποία παρέχει ταυτόχρονα εμπιστευτικότητα και έλεγχο ακεραιότητας του κρυπτογραφημένου κειμένου. Για κάθε κρυπτογράφηση παράγεται νέο τυχαίο διάνυσμα αρχικοποίησης (IV) 12 bytes, το οποίο αποθηκεύεται μαζί με το κρυπτογραφημένο κείμενο. Το κλειδί προκύπτει από μια μυστική τιμή που ορίζεται ως μεταβλητή περιβάλλοντος (SETTINGS_SECRET) και δεν αποθηκεύεται ποτέ στη βάση, ώστε ένα αντίγραφο της βάσης δεδομένων να μην αρκεί για την ανάκτηση των μυστικών. Οι ρυθμίσεις της πλατφόρμας διαβάζονται από τη βάση σε κάθε χρήση, οπότε μια αλλαγή από το web panel εφαρμόζεται αμέσως, χωρίς επανεκκίνηση. Κανένα από τα μυστικά δεν επιστρέφεται μέσω του API· η διεπαφή πληροφορείται μόνο αν έχει οριστεί.
