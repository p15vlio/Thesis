The :backend module translates the architectural decisions of Chapters 4 and 5 into working code: a REST API written in Ktor, organised in explicit layers (routing, service layer, repositories, adapters), with the TenantContext mechanism (§4.3) running through the call chain of every request. This chapter describes how these layers work together in practice: how a request is routed, how the identity of the kiosk device and of the user is confirmed, how the business logic implements the lifecycle of an order and a payment, how the food delivery platforms and the real external services are integrated, and how errors are translated into HTTP responses.

## 6.1 REST API Structure and Routing Layers

The API is exposed exclusively under the /api prefix and is organised in fifteen routing files, each dedicated to one entity or function: HealthRoute, AuthRoutes, OwnerRoutes, PropertyRoutes, DeviceRoutes, ProductRoutes, OrderRoutes, PaymentRoutes, FoodPlatformRoutes, DashboardRoutes, AdminRoutes, AuditLogRoutes, SettingsRoutes, CompanyLookupRoutes and GeocodeRoutes. Each group of routes is defined as an extension function on the Ktor Route, a convention that keeps the routing declarative and readable without annotations (§4.5.2). Some files declare more than one group: OrderRoutes.kt separates the orders as the owner sees them (/orders) from the orders as seen by the device that submitted them (/device/orders), while FoodPlatformRoutes.kt separates the management of connections by the owner (/food-platforms, /properties/{id}/food-platforms) from the catalogue of restaurants that the device reads (/food/restaurants).

Only five endpoints remain outside authentication: GET /health, POST /auth/login and POST /auth/refresh, and two endpoints that serve the bootstrap of a kiosk device before it acquires an identity, namely the resolution of an activation code that has been typed in manually (GET /devices/resolve) and the activation itself (POST /devices/{id}/activate). Four of these accept secrets (a password, a refresh token or an activation code) and are additionally protected by a request rate limit (§6.3). A device's heartbeat (PATCH /devices/{id}/ping) requires the device's own token, so that only it can update its last contact. All the other endpoints are inside an authenticate("jwt") { } block and require a valid JWT. Therefore, creating an order and paying, actions that the kiosk performs on behalf of the guest, require an authenticated device; there is no ordering or payment endpoint that accepts anonymous requests.

One detail of Ktor influenced how the device routes were organised. The device's public endpoints (/devices/resolve, /devices/{id}/activate) and the owner's authenticated endpoints (/devices/{id}, /devices/{id}/deactivate, etc.) share the same prefix. When they were declared as two separate route trees, Ktor matched resolve against the {id} parameter of the authenticated tree and answered 401. For this reason DeviceRoutes.kt declares a single /devices tree, in which only the owner's branches are enclosed in authenticate("jwt").

Table 6.1 groups the endpoints by category, together with whether each category requires a JWT and which roles it accepts.

**Table 6.1: API endpoints by category, JWT requirement and role**

| Category | Endpoints (indicative) | JWT Required | Roles |
|---|---|---|---|
| Platform and device bootstrap | /health, /auth/login, /auth/refresh, /devices/resolve, /devices/{id}/activate | No | — |
| Kiosk functions | POST /orders, /device/orders/\*, POST /payments, GET /products, /food/restaurants/\*, GET /properties/{id}, /devices/{id}/ping | Yes | DEVICE |

## 6.2 Device Authentication and the DEVICE Role

The kiosk device has no password or user account; it acquires an identity exclusively through the activation procedure. When the owner creates a new device (DeviceService.create()), an eight-character activation code is generated by a cryptographically secure random number generator (SecureRandom), together with a QR code that encodes, in JSON form, the device identifier, the activation code, the name of the tenant schema and the public address of the API (environment variable PUBLIC_API_URL). At activation (DeviceService.activate()), the service verifies the code and checks that the device's property and owner are both active, answering with 409 otherwise, as for a device that is already activated. The device is then linked to its hardware identifier and the code is deleted in one compare-and-set update, conditioned on activated_at IS NULL and on the code still matching, so that of two simultaneous activations with the same code only one succeeds and the other receives 409. Finally a JWT access token is issued with the role claim UserRole.DEVICE and a lifetime of one year (§4.5.7). The token is returned one single time, in the token field of the DeviceResponse; no later read of the device exposes it again.

The alternative activation route, for the case where scanning a QR code is not available, is covered by GET /devices/resolve: the user types the code in manually, and DeviceService.resolveByCode() looks it up in turn in the tenant schema of every registered owner, returning the device identifier and the name of the correct schema, so that the application can proceed to the normal activation. The linear search across all schemas is acceptable for a rare, manual action, but its cost grows with the number of tenants.

Because a device's token is valid for one year, the validity of its signature is not enough. The withTenant function, which every route that needs access to tenant data calls, applies the checks of §4.5.7 to every request with the DEVICE role: 401 for an unknown or disconnected device and 403 for a deactivated device or owner. The device retrieved during the check is placed in an element of the coroutine context, so that the route handlers that need its property (for example the catalogue of products or restaurants) do not look it up a second time. The same element allows POST /orders to check that the property in the request is the device's own, so that a device cannot order on behalf of another property.

The DEVICE role is not treated as equivalent to OWNER: the routes explicitly check the principal's role, or the identity of the calling device, before performing the action. GET /products is a case of dual behaviour: when the request comes from a device, the ProductService returns only the products available at the device's property (taking into account the product_property_overrides table, §5.3.4), while when it comes from an owner it returns the whole catalogue, together with the properties at which each product is deactivated. The role check lives inside the routing handlers, with no intermediate middleware, a conscious choice of simplicity given the small number of roles in the system.

## 6.3 Middleware Pipeline and Error Handling

The order in which the Ktor plugins are installed in Application.module() determines the order in which each request is processed (Figure 6.1): ContentNegotiation (JSON serialisation and deserialisation through kotlinx.serialization), CallLogging, DefaultHeaders, XForwardedHeaders, RateLimit, CORS (open to any origin, with the PUT/DELETE/PATCH/OPTIONS methods and the Authorization/Content-Type headers explicitly allowed), StatusPages for error handling, and finally Authentication with the JWT plugin. RateLimit defines two limits using the token bucket method: the public endpoints that accept secrets allow twenty requests per minute per IP address, so that mass password-guessing attempts are prevented, and address search allows thirty requests per minute per user. Because the web panel reaches the backend through nginx (§7.1), all the browsers' requests would appear to come from the proxy's address; XForwardedHeaders restores the client's real address from the X-Forwarded-For header, which nginx sets to the address of the connection, overwriting any value sent by the client, so that the limit is applied per user and not globally. Before the plugins are installed, the application's start-up creates the tables of the public schema and updates the schema of each existing tenant (§5.1).

The StatusPages plugin translates every exception into a structured ErrorResponse, with a fixed error code and the corresponding HTTP status (Table 6.2).

**Table 6.2: Mapping of exceptions to HTTP responses**

| Exception | HTTP | Code | Typical Case |
|---|---|---|---|
| AuthenticationException | 401 | UNAUTHORIZED | Wrong password, expired refresh token, inactive account |
| ForbiddenException | 403 | FORBIDDEN | Wrong role, an order of another device, wrong activation code, deactivated device, device of a deactivated owner |
| NotFoundException | 404 | NOT_FOUND | Non-existent entity |
| ConflictException | 409 | CONFLICT | Invalid status transition, an order already paid, duplicate email |
| IllegalArgumentException | 400 | BAD_REQUEST | Validation failure (e.g. minimum order not met) |
| Deserialisation error | 400 | BAD_REQUEST | Malformed request body; fixed message with no internal details |
| ExternalServiceException | 502 | EXTERNAL_SERVICE_ERROR | The company registry, the geocoding service or a platform did not respond or rejected the key |
| Rate limit exceeded | 429 | TOO_MANY_REQUESTS | Many login attempts or address searches within a minute |
| ExposedSQLException (uniqueness or foreign key violation) | 409 | CONFLICT | Concurrent duplicate request or deletion of a record referenced elsewhere |
| Any other exception | 500 | INTERNAL_SERVER_ERROR | Unexpected error |

In the last case, the exception's message is never passed on to the client; it is recorded in full in the server's log, while the client receives a fixed, generic message, so that any leak of internal SQL or database driver details is ruled out. Mapping the database's constraint violations to 409 ensures that the constraints of §5.5 act as the last safeguard, with the appropriate response, even when two requests bypass a service-layer check at the same time.

The TenantContext is not installed as a plugin in the pipeline. It is applied explicitly per route through two extension functions of the ApplicationCall: call.tenantSchema() extracts the schemaName claim from the JWT (or, for the Platform Admin, who belongs to no tenant, from a request parameter), and call.withTenant { } runs the handler's body in a coroutine scope enriched with TenantContext(schema), also performing the revocation check for devices (§6.2). The devices' public endpoints build the TenantContext from the schema value of the request or the lookup, since there is no JWT yet; the schema name is always checked for its format before it is used (§4.3). Making the call explicit is consistent with Ktor's philosophy (§4.5.2): each route states explicitly that it needs a tenant context, with no hidden behaviour.

## 6.4 Service Layer and Dependency Assembly

Every route stays thin: it validates the input, obtains the parameters and immediately hands them over to the corresponding service. The business logic lives in the service layer: AuthService, OwnerService, PropertyService, DeviceService, ProductService, OrderService, PaymentService, RefundService, FoodDeliveryService, FoodOrderEventHandler, DashboardService, PlatformSettingsService and AuditLogService. Each service receives through its constructor the repository interfaces, port interfaces (§4.4) and other services it needs; some also use backend helpers directly, such as tenantQuery for transaction boundaries (§4.2). The configureRouting() function is the only point in the code where the specific implementations (ExposedOrderRepository, EmulatedPaymentAdapter, SmtpEmailAdapter and so on) are created and connected to one another through their constructors (manual wiring), with no dependency injection framework. The same function is registered on the application's shutdown event, so that the adapters' HTTP clients are closed and the background jobs are cancelled.

AuthService is where the authentication justified in §4.5.7 is applied. login() accepts a declared role (PLATFORM_ADMIN or OWNER), looks up the corresponding account by email without distinguishing case, verifies the password through BCrypt and issues an access/refresh token pair. A deactivated owner is rejected, with the check made after the password has been verified, so that the state of the account is revealed only to someone who knows the password. The DEVICE role is explicitly rejected by the login procedure. refresh() computes the SHA-256 hash of the token the client sent, looks up the corresponding record, checks its expiry and deletes the old token before issuing a new pair, checking again that the owner is still active. The changePassword() method lets the logged-in user change their password: it verifies the current password, requires at least eight characters for the new one, deletes all of the user's refresh tokens so that their other sessions can no longer be refreshed, and returns a new pair of tokens for the current one. A wrong current password is returned as 400 and not as 401, because the web panel interprets every 401 as the end of the session and would log the user out (§7.5).

OwnerService coordinates the onboarding of a new owner: it validates the details (the VAT ID must consist of nine digits), normalises the email, creates the record with the BCrypt hash of a random twelve-character password, creates the tenant schema and, finally, sends the welcome message. If creating the schema fails after the record has already been saved, the owner is automatically deactivated, so that an active account without a valid schema is not left behind. Manually deactivating an owner also deletes all of their refresh tokens, so their access ends from the next request (§6.2). Finally, the resetPassword() method serves the owner who has forgotten their password: it generates a new temporary password, deletes the owner's refresh tokens, sends it to them by email and returns it once to the administrator.

## 6.5 The Order Lifecycle

An order's lifecycle is enforced by the isValidTransition() method of the OrderService, which implements the state machine of §3.2.6 (Figure 6.2): PENDING → CONFIRMED → PREPARING → OUT_FOR_DELIVERY → DELIVERED. From the final states (DELIVERED, CANCELLED) no transition is allowed, a transition to CANCELLED is allowed from any non-final state, and every other transition must follow the order of the cycle exactly. Two rules further restrict the manual transitions. An order in the PENDING status is unpaid and can only be cancelled; the transition to CONFIRMED is performed exclusively by the PaymentService after an approved payment (§6.6). The progress of a food order is updated by the delivery platform (§6.7), so for it the only manual action is cancellation. A third rule concerns cancellation from the device: the guest can cancel an order only while it is in the PENDING or CONFIRMED status, that is, before its preparation begins; from then on, cancellation and the refund are the owner's decision. Every illegal transition is rejected with a ConflictException, mapped to HTTP 409.

![Figure 6.2: Order state machine — allowed transitions and who triggers each one (payment, owner, platform).](/media/fig-6-2-order-state-machine.png)

The status is updated with compare-and-set (§5.6): if the order changed in the meantime (because of a payment, a platform event or a second cancellation), the update is not applied and the caller receives a 409 response, so that it refreshes its data. When an order is cancelled, a refund of every approved payment for it is requested through the RefundService (§6.6). For a food order the cancellation runs entirely in a non-cancellable context (NonCancellable) and follows a fixed order: the status first changes to CANCELLED with compare-and-set, the delivery platform is then asked to cancel the order, and if it refuses, the status returns, again with compare-and-set, to the previous one and the request is answered with 409 without a refund; only after the platform has accepted the cancellation is a refund of the approved payments requested. A paid food order that does not yet have the platform's identifier, because its placement is still in progress (§6.6), cannot be cancelled: both the owner's route and the device's route answer with 409 ("The order is being placed with the delivery platform, try again in a moment"). Five minutes after the order's last update (PLACEMENT_GRACE_MS) the placement is considered failed, for example because of a restart during the call, and the cancellation is allowed again.

Creating an order (OrderService.create()) starts with validation: the order must have at least one item and every quantity must be between 1 and 99, while the guest's email, if given, must be a valid address of at most 255 characters and the notes must not exceed 1,024 characters. The client sends only identifiers and quantities; prices are always derived on the server, from the owner's catalogue for an IN_ROOM_STORE order (where it is also checked that each product is available both overall and at the specific property, §5.3.4) or from the platform's menu for a FOOD_DELIVERY order, to which the restaurant's delivery cost is also added. The order and its lines are written in one transaction (§5.6), so that a failure at any point undoes the whole sequence. The order is stored in the PENDING status and returned to the device with the final amount, so that the payment concerns exactly the amount the server calculated.

The OrderService's read methods serve the list of a property's orders for the owner, the history of a specific device and filtering by status. The path /device/orders/{id} limits the reading and cancelling of an order to the device that created it, through the requireDeviceId parameter: if the device identifier in the JWT does not match the order's deviceId, the call is rejected with a ForbiddenException.

## 6.6 Connection to the Payment Provider

Charging, approval and refunds are the responsibility of the payment provider, with which the backend communicates only through the PaymentGateway port (§4.4). The system's responsibility is to request each action exactly once and to record the outcome.

Payment is a separate step from creating the order: once the order has been created, the kiosk calls POST /payments with its identifier, the way the card was read, the result of the cardholder verification and, where available, the last four digits of the card. PaymentService.initiate() performs the check, the approval and the recording within one transaction that starts by locking the order's row (SELECT … FOR UPDATE, §5.6). A concurrent second payment attempt, for example a repeat of the request after a network delay, therefore finds the order already paid and is rejected with 409 before it reaches the payment acquirer.

Inside the transaction, the service verifies that the order belongs to the device that is paying, that it has not already been paid and that it is in the PENDING status, and requests approval from the PaymentGateway. The response is recorded as a new payment record. A decline is treated as a normal outcome of the payment: the record is stored as FAILED with the reason for the decline, the order stays PENDING and the response is returned to the kiosk, which informs the guest and waits for a new card. An approval is stored as COMPLETED together with the transaction identifier and changes the order to CONFIRMED.

After approval, the provider has already charged the card and the rest of the processing is executed in a non-cancellable coroutine context (NonCancellable), so that an interruption of the request by the client does not leave the processing incomplete. For a food order, the service now submits the order to the platform (§6.7). If the platform does not accept it, the service cancels the order with a compare-and-set from CONFIRMED to CANCELLED and requests a refund of the amount only if this update succeeds, so that an order cancelled in the meantime is not refunded a second time; the response to the kiosk contains, together with the approved payment, the order's status and a message for the guest. If the order carries an email, the receipt is sent in a separate coroutine scope, so that a slow or unavailable SMTP server does not delay the payment's response.

RefundService brings together the refund requests for all cases of cancelling a paid order: by the owner, by the guest or because of the platform's refusal. It first claims the payment with a compare-and-set from COMPLETED to REFUNDED, and only the caller that wins the claim requests the refund from the PaymentGateway with the identifier of the original transaction; a concurrent second attempt for the same payment loses the claim and sends no request, so a second refund is not requested for the same payment. If the gateway fails, the payment is reset to COMPLETED. The action is recorded in the audit log with the amount and the transaction identifier. RefundService does not interrupt the cancellation with an exception: a failed refund is recorded in the audit log as requiring manual action, while the order's cancellation completes normally.

The EmulatedPaymentAdapter answers in place of a real acquirer: it approves or declines a transaction depending on the way the card was read and completes every refund successfully (§3.4.1). Because the adapter produces both approvals and declines, both branches of the payment flow, as well as the refund, can be observed in the prototype.

## 6.7 Integrating Food Delivery Platforms

FoodDeliveryService coordinates all interactions with the delivery platforms, through one adapter per platform that implements the FoodDeliveryProvider port. When an owner connects a platform, it asks the adapter to verify the access key and, on success, stores it encrypted in the food_platform_connections table (§5.3.8). The owner then sets which of the connected platforms are offered at each property; the service rejects a platform that has not been connected. Disconnecting a platform is rejected while it has orders in progress, since its key is needed for a possible cancellation.

For the device, the service returns the restaurants of all the platforms enabled at its property and the menu of a restaurant, each time using the owner's decrypted key. When a food order is created, the priceOrder() method checks that the platform is available at the property, prices each dish from the current menu and verifies the restaurant's minimum order. After the approved payment, the placeOrder() method submits the order to the platform together with the delivery address, which is built from the property's details (street, floor, name on the doorbell, phone), and records the identifier the platform returns, provided the local order has not been cancelled in the meantime. If this recording fails, or the order was cancelled while the platform call was running, the service cancels the order on the platform (best effort) before reporting the error, so that an order that the system cannot track or cancel is not left on the platform.

The progress of an accepted order reaches the system through the FoodOrderEventListener port, which is implemented by the FoodOrderEventHandler. Because the platform's events are not tied to any HTTP request, each event carries the name of the tenant schema, from which the handler restores the TenantContext. The handler applies a new status only if it comes after the current one in the lifecycle and only with compare-and-set, so a late or duplicate event, or an event for an order that was cancelled in the meantime, is ignored. Together with the status, the estimated delivery time reported by the platform is also stored.

The three emulated platform adapters share their logic in the EmulatedFoodPlatformAdapter class and differ only in the platform's name and in their data files, which contain the platform's restaurants, menus and product catalogue. For each accepted order, the adapter starts a coroutine that, at regular intervals (environment variable FOOD_PLATFORM_STEP_SECONDS, default 45 seconds), reports the statuses PREPARING, OUT_FOR_DELIVERY and DELIVERED in turn through the FoodOrderEventListener, exactly as the notification address of a real platform would. Because these timers exist only in memory, the EmulatedFoodOrderRecovery class looks up, at application start-up, in each tenant, the food orders that were in progress and schedules their remaining steps again; an error in one tenant does not prevent the recovery of the others. A real platform keeps its own state and would not need an equivalent mechanism.

Each platform's product catalogue also serves a second function: the owner can import selected items from it as products of their own store. ProductService always takes the prices from the platform and not from the client, skips the items that already exist in the catalogue with the same name and returns which ones were imported and which were skipped.

## 6.8 Real External Services: Email, Company Registry and Geocoding

The three adapters connected to real services follow common principles. Every network call has a timeout, so that an unavailable service does not tie up a request indefinitely, and every failure is translated either into an ExternalServiceException (HTTP 502 with an understandable message) or, where the service is not essential to the user's action, into a log entry without interrupting the flow. Their settings (SMTP server, registry key) are read from the PlatformSettingsService on every use, so a change from the web panel's settings page is applied immediately.

SmtpEmailAdapter implements the NotificationService port with the Jakarta Mail library, composing and sending messages over SMTP [8] with the connection security the administrator has chosen (STARTTLS, SSL or none). It supports three notifications, the receipt for an order, the welcome message for a new owner and the message of a password reset, which never throw an exception: if no server has been set or sending fails, the failure is recorded in the log and the user's action (a payment or the creation of an owner) completes normally. Sending a test message from the settings page is the exception, since there the error is returned to the administrator so they can correct the settings. In the logs, email addresses appear partially masked, so as to allow correlation without exposing the guest's personal data.

The adapter of the CompanyRegistry port looks up a business by VAT ID in the company registry's open data API [9]. Because a VAT ID can correspond to both the registered seat and to branches, the adapter prefers the record of the seat, and from the business's activities it chooses the main one. A key that has not been set or is rejected, exceeding the request limit and the unavailability of the service are each reported to the administrator with a different, understandable message.

The adapter of the Geocoder port offers two functions: searching for an address from free text and converting coordinates into an address (reverse geocoding), which is used when the owner selects their current location. The usage policy of the public geocoding service [10], [24] requires an application identifier on every request, at most one request per second and avoiding search while typing. The adapter observes the limit at process level through a shared Mutex, which remains acquired for the whole duration of each request, so that calls are executed strictly one after the other and at least one second apart. Waiting for the Mutex is limited to ten seconds: when many searches arrive at the same time, those that would wait longer are rejected immediately with an understandable message instead of piling up, and in combination with the per-user limit (§6.3) a single user cannot block the service for the others, while the web panel runs a search only when the user explicitly asks for it. The results are converted into the individual address fields (street, number, postal code, area, city) and the coordinates, with which the property's form is filled in.

## 6.9 Event Logging and the Action Log

The backend has two distinct levels of recording, with a different purpose and a different audience. The first is technical logging through the Logback library on top of the SLF4J interface, which is aimed at whoever operates the server. Ktor's CallLogging plugin records every request, while each service and adapter uses its own logger for the important events: the approval or decline of a payment, the failure of an email send, the failure to submit an order to a platform, or a platform event that was ignored because the order had already changed. Unexpected errors are recorded with a full stack trace, together with the request's method and path (§6.3). Personal data is deliberately limited: guests' email addresses appear partially masked, the email address is not recorded at login, and sensitive card data does not reach the server.

The second level is the action log (audit log, §5.2.4), which is aimed at the Platform Admin and records the actor, the action, the tenant and the time. 27 types of actions are recorded, covering the owners' lifecycle (creation, update, deactivation, reactivation, password reset), the user's own password change, properties (creation, update, deactivation, activation, deletion), devices (creation, deactivation, reactivation, disconnection, deletion, bulk deactivation along with the property), the deletion and import of products, availability per property, connecting and disconnecting delivery platforms, the choice of platforms per property, changes to the SMTP and company registry settings, and refunds. For the settings, the audit log records that a secret value changed without recording its value. For refunds, it records the amount, the transaction identifier and the outcome, so that a failed refund can be found and completed manually. The Platform Admin reads the log through GET /audit-logs, in pages of fifty records.

The choice of what is recorded is a conscious one: the audit log covers administrative actions and refunds, not the ordinary flow of orders. The changes of an order's status are already recorded in the orders table itself (status and time of last update), while a food order changes status automatically several times, so recording every transition would flood the log with low-value entries. The price of the choice is that the system does not keep a full history of who advanced an order of products at each stage.

## 6.10 Security Hardening

Beyond the authentication mechanisms of §4.5.7, the backend applies a series of measures concerning the points where data from the client reaches the database or the payment logic. Many of them came out of a systematic quality and security review of the code carried out during development, which identified specific findings that were fixed before completion.

The most significant finding concerned the choice of the tenant schema. The devices' public activation endpoints accept the schema name as a request parameter, and an initial implementation embedded it without a check in the SET search_path statement, allowing an anonymous user to inject arbitrary SQL text. The fix was applied at a single point, which every access to a tenant schema passes through: before any use, the name is checked against the only form that the system ever generates (tenant\_ followed by twelve hexadecimal characters), and any other value is rejected with 400 (§4.3). The verification in §9.3 includes exactly such an attempt.

The remaining measures can be summarised as follows. Cryptographic values (temporary passwords, activation codes) are generated by a cryptographically secure generator (SecureRandom). The JWT signing secret and the settings encryption secret are mandatory environment variables, with no default value in the code, so that a missed setting prevents start-up instead of silently leading to a known, public value. There is no path that reads a token's claims without checking the signature. The routes that change data explicitly check the caller's role, and the device endpoints check that the order or the property belongs to the device making the request. Prices are always calculated on the server from the catalogue or the menu, while the client sends only identifiers and quantities, limited to the range 1 to 99; in this way a modified kiosk cannot set its own price. Errors do not leak internal details to the client (§6.3), and the parameters embedded in the addresses of external services are encoded, while those services' addresses are fixed in the code, so a user cannot direct the server to an arbitrary destination.

A final security review of the code, after the addition of the delivery platforms, the refunds and the real external services, found no critical issues in the areas examined: the isolation between tenants, the role checks, the calculation of prices, the encryption of the secrets and the calls to the company registry and the geocoding service showed no problems. The lower-severity findings it identified (the ability to cancel from the device an order that was already being prepared, the omission of the per-property availability check when creating an order, and the absence of a rate limit on login and on address search) were fixed and verified (§6.5, §6.3, §9.3).

## 6.11 An Example of a Full Request Cycle

To make the interaction of the layers described above concrete, it is useful to follow a single POST /api/orders request from its arrival at the server to the response to the kiosk. The request first reaches the Authentication plugin, which verifies the JWT's signature and extracts the JWTPrincipal; if the token is invalid or has expired, the chain is interrupted immediately with a 401 response, without ever reaching the route. Then the handler checks that the principal's role is DEVICE, reads the propertyId parameter from the query string and the device identifier from the JWT's subject claim, deserialises the request body into a CreateOrderRequest and calls call.withTenant { }. withTenant enriches the coroutine scope with the TenantContext that corresponds to the token's schemaName claim, verifies that the device is still active and allows the handler to check that the propertyId is the device's property.

Inside this scope, OrderService.create() performs the sequence of steps of §6.5: validation of the items, pricing from the owner's catalogue through the ExposedProductRepository (which runs its query in the correct tenant schema thanks to the active TenantContext, without the repository class itself knowing anything about multi-tenancy) or from the platform's menu through the FoodDeliveryService, calculation of the total amount and insertion of the order and its lines in one transaction. If any step fails, for example if a product is no longer available or the minimum order is not met, the corresponding exception is thrown, no partial write remains in the database, and the exception escapes up to StatusPages, which translates it into a structured ErrorResponse. If all the steps complete normally, the handler answers with 201 Created and the order in the PENDING status, ready for the device's next request, POST /payments. This entire chain (authentication, role-based authorisation, revocation check, tenant schema resolution, execution of the business logic and error translation) passes through four different levels of code, each with its own responsibility, following the structure of Chapter 4.
