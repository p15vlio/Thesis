The :owner-web module implements the management panel used by the two authenticated human roles of the platform, the Platform Admin and the Owner (§3.1.1, §3.1.2). The choice of Compose Multiplatform with a wasmJs compilation target instead of an established JavaScript framework was already justified in §4.5.5, where the reasoning behind the decision against alternatives such as React or Vue was discussed. This chapter describes how a single-page application written entirely in Kotlin is organised in practice, from the build stage to the distribution of the final bundle to the browser, the navigation between screens, session management, the division of responsibilities between the two roles, and the screens through which the user makes use of the system's external services.

## 7.1 Build Pipeline and Bundle Distribution

The module is compiled exclusively for the wasmJs target, through the declaration kotlin { wasmJs { binaries.executable() } } in the Gradle build file. It depends on :domain and :data, the same modules the backend uses (§4.1), with the result that the DTOs the client sends and receives (OwnerResponse, PropertyResponse, OrderResponse, CompanyLookupResponse and so on) are literally the same Kotlin classes that the backend serialises. No manual mapping of types is needed at the client-server communication point, nor any intermediate OpenAPI schema or code generation tool; the type safety of this contract follows directly from the sharing of source code described in §4.5.4.

The module is compiled through the Gradle task wasmJsBrowserDevelopmentDistribution, which produces a set of static files (HTML, a JavaScript loader and the binary .wasm file). In the context of the Docker Compose deployment (§9.2), this step is carried out in the first stage of a multi-stage Docker image: a container based on JDK 21 takes care of compiling both the backend (:backend:installDist) and the owner-web bundle, while the generated content is copied into a separate, lightweight nginx:alpine container that serves solely as the web server. The nginx.conf configuration file defines two routing rules: every request to the root (/) is served from the bundle's static files, while every request to the path /api is forwarded (proxy_pass) to the backend's container. In this way nginx acts at the same time as a static web server and as a reverse proxy, allowing the browser to address one single origin both for the static files and for the REST API calls, with no CORS issues.

There is no server-side rendering and no multiple HTML pages: the whole application is rendered inside a single \<canvas> element through the Compose renderer, and the entry point Main.kt merely initialises the runtime and calls the root composable App(). The organisation of the source code follows a separation by responsibility: the screen/ directory contains the application's screens, ui/ the reusable visual elements, auth/ login and session management, api/ communication with the backend and util/ formatting helper functions.

## 7.2 Navigation: The Screen Model

Navigation is not based on an external routing library nor on URL-based navigation with browser history, but on a simple, closed model of states: the sealed class Screen enumerates every possible screen of the application. Most screens carry no parameters and are declared as objects (e.g. Login, Dashboard, PropertyList, FoodDelivery, AdminDashboard, Settings), while the screens that need navigation context are declared as data classes: DeviceList(propertyId, propertyName) and OrderList(propertyId, propertyName) carry the property for which devices or orders are shown, while AdminOwnerView(ownerId, schemaName, displayName) carries the identity of the tenant that the Platform Admin chose to manage.

The root composable App() holds the current screen in a mutableStateOf\<Screen> and a single when block decides, based on this value, which composable to render. This approach is consistent with Compose's declarative model: every change of the state automatically triggers a re-composition of the interface tree, without manually switching views. The navigation function navigate(screen: Screen), passed as a parameter to every screen, simply assigns a new value to this state. There is no back stack, route history or deep linking, since the application is aimed at a closed set of administrative screens and not at a public website; returning to a previous level is done through the navigation bar (breadcrumb) at the top of the nested screens.

The initial screen after a successful login is determined by the user's role: AdminDashboard is returned for the PLATFORM_ADMIN role and Dashboard for the OWNER role. The same logic applies when the user reloads the page with an already stored session (§7.5): there is no common home page, but a different entry point per role.

## 7.3 Main Screens by Role

The Owner has a set of screens focused on their own tenant. The Dashboard presents summary statistics of properties, devices and orders by stage (§3.1.2). PropertyList allows creating, editing, deactivating and deleting properties, with navigation from each record to the devices or orders of that specific property (§7.6). DeviceList, per property, covers creating a device, showing the activation QR code (§3.3.4), deactivation, disconnection and the order history of each device. ProductList manages the tenant's product catalogue, including availability per property (§5.3.4) and importing products from a platform's catalogue (§7.7). FoodDelivery manages the connections to the delivery platforms (§7.7). Finally, OwnerOrders and OrderList present the orders overall or per property, refreshing every 15 seconds, and allow the status to be changed according to the state machine (§6.5).

The Platform Admin has a broader set of screens, adapted to their oversight responsibility. AdminDashboard gathers statistics across all tenants: the number of active and inactive owners, properties and devices, as well as the distribution of orders by status. OwnerList covers the management of owners, that is, creating a new owner with a GEMI lookup (§7.8), editing details and deactivating or reactivating the account. From selecting an owner, the admin goes to AdminOwnerView, a screen that carries the schemaName of the selected tenant as a parameter and serves as the starting point for the screens AdminProperties, AdminDevices and AdminProducts, through which the admin manages the data of any owner without their credentials. AuditLogs exposes the platform's action log (§5.2.4), and Settings the settings of the external services (§7.8). The About and Help screens contain static information.

## 7.4 Role-Based Access and the Side Menu

The separation between Platform Admin and Owner in the web panel works at two independent levels, with a clear distinction between what concerns the user experience and what concerns security. At the interface level, the shared component AppScaffold renders a different side menu depending on the role of the current session: the Platform Admin sees the options Dashboard, Owners, Properties, Devices, Products, Audit Logs, Settings, About and Help, while the Owner sees the options Dashboard, Properties, Orders, Products, Food delivery and Help. At the bottom of the menu, common to both roles, are the password change and logout. This separation improves the user experience, preventing confusion from options that do not apply to the role, without being a mechanism for enforcing security.

The actual enforcement of access is done exclusively in the backend, where every route explicitly checks the role carried by the request's JWT before performing any action (§6.1, §6.2). Even if the client-side UI were bypassed, for example through a direct call to the API, the server would reject the request with an authorisation error, since the access decision does not depend under any circumstances on what the interface shows.

For cross-tenant operations, the client explicitly passes the schemaName of the selected tenant as a query parameter in every call to the backend; methods such as listPropertiesAdmin, createProductAdmin or deactivateDeviceAdmin accept the schemaName as an explicit parameter and append it to the HTTP request. This corresponds to the mechanism of §6.3 for the Platform Admin, who carries no schemaName claim of their own in the JWT, since they belong to no tenant, but is allowed to specify it explicitly per request.

## 7.5 ApiClient: Communication and Token Renewal

Communication with the backend goes through a single ApiClient class, which wraps a Ktor HttpClient with a Js execution engine and exposes one method per functional endpoint, for example listOwners(), lookupCompany(), searchAddress(), connectFoodPlatform(), updateOrderStatus(). The class installs a ContentNegotiation plugin for automatic JSON (de)serialisation and a custom HttpResponseValidator, which converts unsuccessful responses into exceptions carrying the backend's error message, excluding the 401 code, so that it is detected separately by the token renewal mechanism.

Every authenticated call goes through an internal function withTokenRefresh: if the backend answers with a 401 code, the client automatically tries to renew the session by calling /api/auth/refresh with the stored refresh token, before repeating the original request exactly once with the new access token. Because refresh tokens rotate on every use (§4.5.7), two requests that receive a 401 at the same time must not renew the session independently; the second would use an already consumed token and would wrongly end the session. For this reason the renewal is protected by a Mutex: the first request carries out the renewal and the others use its result. If the renewal fails, or if there is no stored session, the client signals the end of the session. From the client's side, this mechanism transparently implements the refresh token rotation scheme: the user does not notice the renewal, except if it fails as well.

The session, represented by the AuthSession class (access token, refresh token, role, schemaName), is stored in the browser's localStorage so that it survives a page refresh. The end of the session is handled through a simple reactive singleton, SessionController, which exposes a mutableStateOf\<Boolean> value indicating whether the session has expired. The root composable App() watches this value through a LaunchedEffect: as soon as it becomes true, it clears the local session, shows an informational message, returns the user to the login screen and resets the value. No individual screen needs to check by itself whether its session has expired; this responsibility is gathered in one single place.

Storing the tokens in localStorage is simple but makes them accessible to any JavaScript code running on the same page. This risk is limited by the access token's short lifetime and by the absence of third-party code on the page, but it remains one of the known limitations of the prototype (§9.4).

## 7.6 Property Management: Address Search and Guest Information

The PropertyList screen, both in its Owner version and in the corresponding cross-tenant version for the Platform Admin (AdminProperties), is a representative example of how a management form is organised in the panel. The form for creating or editing a property collects the name, the address (street, number, postal code, optional area, city and floor), the name on the doorbell, the contact phone and optional notes. Each field is mapped to mutable state (remember { mutableStateOf(...) }) inside the form's composable, and confirmation is enabled only when all the required fields hold a value. On confirmation, the data is packaged into a CreatePropertyRequest or UpdatePropertyRequest, the same DTOs of the :data module that the backend consumes.

The address does not have to be typed field by field. The AddressSearch component offers two ways of filling it in: the user types an address and presses the search button, or chooses to use their current location, in which case the application requests the coordinates from the browser's Geolocation API. Because this API is not exposed directly to Kotlin/Wasm code, it is called through a small JavaScript function declared with the @JsFun annotation, and its result is converted into a Kotlin suspend function. The same technique is used at a few other points where the web panel needs browser capabilities that the Kotlin libraries do not cover. In both cases the request goes through the backend (§6.8), which queries the Nominatim service and returns one or more addresses; selecting an address fills in the individual fields and the coordinates, which the user can correct. The search runs only on an explicit action by the user and not while typing, in line with the service's usage policy. Because browsers allow the Geolocation API only on secure connections (HTTPS) or on localhost, a failure to determine the location is reported to the user, who can always fall back on a text search.

The same form includes two more sections. The GuestInfoFields component collects the optional information that the kiosk application shows the guest (the Wi-Fi network and password, the check-out time, the house rules), and the FoodPlatformControls component shows a checkbox for each delivery platform the owner has connected, so that it can be set which ones are offered at the property. The AdminProperties screen reproduces the same form, with the only difference that every call to the backend is accompanied by the schemaName of the tenant selected through AdminOwnerView (§7.4).

## 7.7 Delivery Platforms, Product Import and Orders

The FoodDelivery screen presents one card for each supported platform (efood, Wolt, Box), with the state of the connection. To connect a platform, the owner enters the access key the platform has given them; the backend verifies it with the platform before storing it encrypted, so a wrong key is rejected immediately. The key is never returned to the interface. Disconnecting asks for confirmation and is rejected by the backend while the platform has orders in progress (§6.7).

From the products screen, the ImportProductsDialog dialog lets the owner pick a connected platform, browse its product catalogue and mark the items they want to add to their accommodation's store. After the import, the dialog reports which items were added and which were skipped because they already existed in the catalogue. The prices of the imported items always come from the platform and can later be changed like any other product.

In the order screens, each food order is shown with the platform and the restaurant it comes from. The status change dialog offers only cancellation for these, with an explanatory message that the progress is updated by the platform, while for the accommodation's own orders it offers the next permitted status. The permitted options are computed on the client for convenience; the check that counts is the backend's (§6.5). The PaymentSection component shows, for each order, the payment attempts in the order they were made: the way the card was read, its last digits where available, the outcome, the reason for a decline and the refund after a cancellation.

## 7.8 Owner Onboarding and Platform Settings

The owner creation form on the OwnerList screen starts from the VAT ID. The administrator types the VAT ID and chooses search; the client calls lookupCompany(), the backend queries GEMI (§6.8), and the details that are returned (company name, trade name, GEMI number, legal form, business activity, address of the registered seat) are filled into the corresponding fields. The administrator checks them, fills in the contact person's details and saves. If the search fails, the backend's message is shown in the form and the fields can be filled in manually. After saving, a dialog shows the new owner's temporary password once, with the ability to copy it, in case the welcome message has not arrived.

The list of owners also offers resetting the password of an owner who has forgotten it. After confirmation, the backend generates a new temporary password and sends it to the owner (§6.4), while the same dialog that appears on creation shows the password once to the administrator. The owner, in turn, replaces the temporary password with their own through the password change dialog in the side menu, which asks for the current password and the new one twice, and enables the save button only when the new password has at least eight characters and the two values match. After a successful change, the client stores the new pair of tokens returned by the server, so that the current session continues while the others are terminated.

The Settings screen, available only to the Platform Admin, gathers the settings of the platform's external services. The email section collects the SMTP server, the port, the type of connection security, the credentials and the sender's address and name, with pre-filled values for a Gmail account, and offers sending a test message to any address. The GEMI section collects the access key. For the secret values (the SMTP password, the GEMI key), the screen shows only whether they have been set; if the SMTP password field is left empty when saving, the existing password is kept, so that the administrator can change the other settings without typing it again. The same screen states the lifetime of the tokens (15 minutes for user sessions, 30 days for refresh tokens, one year for kiosk devices).

## 7.9 Data Refresh, Errors and Concurrent Actions

A management application running in the browser faces three issues that are not visible in a static description of the screens: how the data stays up to date, how errors are presented, and how double execution of an action is prevented.

The owner's order screens and the administrator's orders tab refresh their data every 15 seconds. The refresh is implemented as a loop inside a LaunchedEffect, so the loop lives as long as the screen: when the user moves to another screen, Compose cancels the coroutine and the loop stops, without continuing requests in the background. For this cancellation to work, every place that catches exceptions while loading data explicitly rethrows the CancellationException instead of treating it as a network error. An omission at this point would keep the loop alive after leaving the screen, a bug that was found in a review of the code and fixed systematically across all screens (the pattern now appears in more than forty places in the module).

The backend's errors reach the interface as exceptions carrying the message of the ErrorResponse (§6.3) and are presented in a uniform way: loading errors as an ErrorBanner box at the top of the screen, which the user can close, and the results of actions as transient SnackbarController messages. Because the backend's messages are short and understandable (for example "Cannot delete a device with existing orders — deactivate it instead"), the interface can show them as they are, without its own catalogue of messages per error code.

Double execution of an action is prevented at two levels. In the interface, the confirmation dialog disables its buttons after the first press, and dialogs close both on success and on failure of the action, so that a dialog is not left "stuck" with disabled buttons. In the backend, the critical actions are protected anyway by the mechanisms of §5.6, so even two concurrent requests from two open browser tabs cannot advance the same order twice.

For the purposes of the demonstration, the login screen includes a quick-login section with two buttons, for the administrator account and for the test owner created by the scripts of §9.2. These are demonstration accounts with published passwords, and the section would be removed in a real installation.

## 7.10 Reusing Visual Components

Beyond the screens, the :owner-web module organises a set of shared visual components in the ui/ directory, which prevent repeating interface code across screens with similar needs. FormDialog provides a general modal frame with standard confirm and cancel buttons, on which all the forms for creating and editing entities are built. ConfirmDialog covers the actions that require confirmation, such as deleting or deactivating a record, and disables its buttons after the first press, so that a double click does not perform the action twice. QrCodeDialog shows the activation QR code of a new device (§3.3.4, §8.2), while SnackbarController offers a single mechanism for showing transient messages. AddressSearch, GuestInfoFields, FoodPlatformControls, ImportProductsDialog and PaymentSection (§7.6, §7.7) are used both in the owner's screens and in the corresponding screens of the administrator. Components such as ActiveBadge, StatusChip, ErrorBanner, EmptyState and LoadingState standardise how the activation state, the order status, error messages, empty lists and loading states are shown, so that every screen follows the same visual language.

## 7.11 Summary

The :owner-web module confirms in practice the benefits of the architectural decision of §4.5.5: one language and a single UI programming model cover both the Android kiosk application (Chapter 8) and the web management panel, with direct reuse of the :data DTOs and no intermediate conversion layers. The simplicity of the navigation model based on a sealed class, the clear separation of the two roles both at the interface level and at the level of authorisation in the backend, the centralised handling of session renewal and expiry, and the screens that make use of GEMI, geocoding and the delivery platforms, make up a management application that, without an established JavaScript framework, covers the functional needs of both the Owner and the Platform Admin.
